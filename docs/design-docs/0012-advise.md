## 1. 背景と目的

M2 までで、アクションは「何が起きたか」（事実の整理、0001 の 2-a）だけを出す。利用者の困りごとの 3 つ目「やるべきことがまとまっていない」を解消するには、**「どう判断すべきか」の材料**（2-b）が要る。

本書では、ルール生成のアクションに対してエージェントが **助言** を付ける仕組みを決める。助言は判断そのものではなく判断材料であり、最終判断は人が行う（0001 R5）。AI はツールの外（スキル）に置く（0001 P3）。

## 2. スコープ / 非スコープ

### スコープ

- `advise` ツール: 助言がまだ無い未対応アクションを、判断に必要な事実と一緒に JSON で出す。助言を書き込む
- `.agents/skills/advise/SKILL.md`: 助言の書き方（構成、根拠、禁止事項）
- ダッシュボード: アクションの行に助言を表示。ルール生成と AI 生成の区別、免責の注記
- 朝の運用手順の更新: `assess` → `detect run` → `advise`

### 非スコープ

- 助言の自動評価（助言どおりにしたらどうなったか）。M5 の振り返り
- 攻め（買い検討の助言）。M4 でウォッチ銘柄の `valuation_cheap` 等に同じ仕組みを使う
- 助言の自動実行（launchd から `claude -p`）。0011 の U1 と同じく後で検証

## 3. 設計

### 3.1 助言の位置づけ

| | ルール生成のアクション（既存） | 助言（本書） |
| --- | --- | --- |
| `origin` | `rule` | `ai` |
| 内容 | 何が起きたか（事実の整理） | どう判断すべきか（論点、選択肢、確認すべきこと） |
| 作る人 | `detect run` | エージェント（スキル `advise`）が CLI 経由で |
| 対応関係 | シグナル 1 つに 1 つ | **ルール生成のアクションと同じ `signal_id`** を持つ。`(signal_id, origin)` の一意制約で二重に付かない |
| 表示 | 一覧の 1 行 | **同じ行の中に「助言」として表示**（別の行にしない）。一覧は「1 行 = 1 つの出来事」を保つ |
| 状態 | `open` / `done` / `dismissed` | ルール生成のアクションに従う。人がルール側を対応済みにしたら、同じ `signal_id` の助言も同じ状態にする |

### 3.2 `advise` ツール

```
pnpm advise pending [--limit 20]      # 助言が無い未対応アクションを、事実の束と一緒に出す
pnpm advise record --input <file|->   # 助言を書き込む（配列）
```

`pending` の 1 項目に含める事実（**エージェントはこれ以外を材料にしない**）:

| 項目 | 内容 |
| --- | --- |
| `action` | ルール生成のアクション（id、kind、重大度、title、body、作成日） |
| `instrument` | 銘柄、保有（数量、平均取得単価、口座）、評価額と含み損益 |
| `quotes` | 直近 30 営業日の株価、60 日高値、200 日線との位置、取得単価比 |
| `score` | 最新のスコアと内訳、直近 30 日の推移（週 1 点） |
| `signals` | 直近 30 日のシグナル（kind、重大度、値、日付） |
| `assessments` | 直近 30 日の有効な判定のうち `relevant` なもの（要約、根拠、対象の見出し・表題・URL） |
| `financials` | 年次 3 期の売上・営業利益・利益率・自己資本比率 |
| `fundamentals` | 最新の PER / PBR / 配当利回り / ROE / 次回決算日 |
| `history` | この銘柄の過去のアクションと対応（done / dismissed とメモ）。「前回はどう判断したか」 |

`record` の入力は `{ actionId, stance, title, body, references, model }` の配列。

| 項目 | 内容 |
| --- | --- |
| `stance` | `hold`（保有継続でよさそう）/ `review`（要確認。判断材料が足りない）/ `reduce`（売却・縮小を検討）。**助言の結論の要約**であり、指示ではない |
| `title` | 1 行。例 `取得単価比 -21% だが、悪化しているのは株価だけ。決算（11/5）まで保有継続が妥当か確認` |
| `body` | Markdown。§3.3 の構成 |
| `references` | 参照した事実の一覧 `{ type: 'news' \| 'disclosure' \| 'signal' \| 'financials' \| 'quote', id?, label, url? }[]`。ダッシュボードでリンクにする |
| `model` | モデル名 |

- `record` は `actions` に `origin = 'ai'`、`signal_id` = ルール生成のアクションの `signal_id`、`title` / `body` を書く。`stance` と `references` は `body` の先頭に機械可読な形（YAML front matter）で埋める（テーブルは変えない）
- 既に助言がある `actionId` は `already_advised` で失敗（全体を失敗にする。0011 の `assess record` と同じ）
- ルール生成のアクションが `open` でなければ `not_open` で失敗

### 3.3 助言の構成（スキル）

```markdown
---
stance: review
references:
  - { type: signal, id: 12, label: "取得単価比 -21%（2026-09-18）" }
  - { type: disclosure, id: 3, label: "業績予想の修正に関するお知らせ", url: "https://..." }
---
## 状況
何が起きているかを 2〜3 文で。事実（数値・日付）だけ。

## 論点
判断を分ける問いを 1〜3 個。例: 「株価の下落は市場全体か、この銘柄固有か」「持つ理由（配当・成長）は崩れたか」

## 選択肢
- 保有継続: どういう前提なら妥当か
- 一部売却 / 売却: どういう前提なら妥当か
それぞれに「確認すべきこと」を添える。

## 確認すること
次に人が見るべき情報（決算日、開示、ニュース）と、その見方。
```

禁止事項（スキルに明記）:
- 事実の束に無い情報を使わない（一般論・記憶にある企業情報・相場観を根拠にしない）
- 目標株価・期待リターン・「買い」「売り」の断定をしない
- `stance` を `reduce` にするのは、事実の束に **企業側の悪化**（判定・財務・開示）があるときだけ。株価の下落だけなら `review` 止まり
- 免責の定型文は書かない（ダッシュボードが表示する）

### 3.4 ダッシュボード

| 画面 | 変更 |
| --- | --- |
| アクション一覧 | 各行に「助言」欄。`stance` のバッジ（`hold` = neutral、`review` = primary、`reduce` = warn）とタイトル。折りたたみで本文と参照リンク。助言が無ければ「未」 |
| 銘柄詳細 | 同上 |
| 共通 | 助言の欄に「AI の助言。判断材料であり、最終判断は人が行う」を常時表示（0001 R5）。モデル名を薄く添える |
| 状態変更 | ルール生成のアクションを `done` / `dismissed` / `open` にしたら、同じ `signal_id` の助言も同じにする（`setActionStatus` を拡張） |

### 3.5 朝の運用（0011 §3.6 の更新）

エージェントに「朝の確認をして」と言うと、`assess` → `detect run` → `advise` の順に実行し、新しいアクションと助言の要約を報告する。これを 1 つのスキル `morning` にまとめる（`assess` と `advise` を順に呼ぶだけ）。

### 3.6 パッケージ構成

| パス | 内容 |
| --- | --- |
| `tools/advise/` | `pending` / `record` |
| `packages/domain/src/advice.ts` | 事実の束の組み立て、助言の読み書き、front matter の解釈 |
| `.agents/skills/advise/SKILL.md`, `.agents/skills/morning/SKILL.md` | スキル |
| `apps/dashboard` | `entities/advice`（stance バッジ、本文の表示）、`widgets/action-table` に助言欄 |

## 4. 検討した選択肢と決定

| 論点 | 決定 | 却下した選択肢と理由 |
| --- | --- | --- |
| 助言の保存先 | `actions`（`origin = 'ai'`、同じ `signal_id`） | 別テーブル `advices`: 0001 で「アクションはルール生成と AI 生成がある」と決めており、既存の一意制約で二重付与も防げる。テーブルを増やす理由がない |
| 一覧での見せ方 | ルール生成の行の中に表示 | 別の行: 1 つの出来事が 2 行になり、対応済みにする操作も 2 回になる |
| `stance` の持ち方 | `body` の front matter | 列を足す: テーブル変更が要る。M5 で集計したくなったら列に昇格する（実装済みの Design Doc を supersede） |
| 事実の束 | ツールが組み立てて渡す | エージェントが自分で CLI を叩いて集める: 集め方がセッションごとにぶれ、根拠の範囲が不明確になる。束にあるものだけ、と線を引ける |
| 助言の自動実行 | 今はしない（人が朝に起動） | `claude -p`: 未検証。0011 U1 と一緒に後で |

## 5. リスク・未決事項

| # | 内容 | 対応 |
| --- | --- | --- |
| R1 | 助言が一般論になり、役に立たない | 事実の束に無いことを書かない、論点は問いの形で、をスキルに明記。`references` が空の助言は `record` で拒否する |
| R2 | 助言が「売れ」「持て」の指示に見える | `stance` は 3 値で断定を避ける。免責を常時表示。`reduce` の条件を絞る |
| R3 | 助言の質を後から測れない | `history` に過去の対応（done / dismissed とメモ）を含め、M5 で「助言と実際の判断・その後の株価」を並べられるようにする |

## 決定事項（壁打ちの結果）

| 論点 | 決定 |
| --- | --- |
| `stance` | hold / review / reduce の 3 値 |
| 表示と状態 | ルール生成の行の中に表示し、状態を連動させる |
| 根拠の範囲 | 事実の束に無いことは根拠にしない（一般的な業界知識も使わない） |
