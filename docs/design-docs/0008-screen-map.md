## 1. 背景と目的

画面が増えていくと「今どんな画面があり、どこからどこへ行けるか」を1枚で見たい。ER 図（0004）と同じく、手で維持する図は古くなるので、**コードから自動生成して固定の場所に置き、古くなっていたらテストで検出する**。

## 2. スコープ / 非スコープ

- スコープ: `apps/dashboard/src/routes/` と、そこから辿れる `<Link to="…">` から画面と遷移を抽出し、`docs/screens.md`（Mermaid）を生成する。各画面の説明は `pages/<page>/ui/*Page.tsx` の先頭の JSDoc から取る
- 非スコープ: 遷移の条件やユーザーフロー（U1〜U6 のようなシナリオ）。それは Design Doc に書く。サーバー関数の呼び出し関係

## 3. 設計

- `pnpm screens` で `docs/screens.md` を生成する。実装は `apps/dashboard/src/app/screens.ts`（抽出と描画）と `scripts/screens.ts`（書き出し）
- 画面（ノード）: `routes/*.tsx` の `createFileRoute('/…')` のパス。`__root.tsx` は除く
- 遷移（エッジ）: ルートファイルから相対 import を再帰的に辿り（FSD の各層を横断する）、`to="/…"` / `to={'/…'}` の文字列リテラルを拾う。辿り着いた先のルートへの遷移とみなす。同じ画面への遷移（タブなど）は自己ループ
- 説明: ルートが import する `pages/<page>` の `ui/*Page.tsx` の先頭 JSDoc（`/** … */`）の1行目。無ければパスだけ
- テスト: 生成結果とコミット済みの `docs/screens.md` が一致すること
- 生成物には「手で編集しない」旨と、画面一覧の表（パス、説明、ページのスライス）を含める

## 4. 検討した選択肢と決定

| 論点 | 決定 | 却下した選択肢と理由 |
| --- | --- | --- |
| 生成元 | ルートファイルと `<Link to>` の静的解析 | `routeTree.gen.ts`: 画面は分かるが遷移が分からない。実行時に DOM から収集: データがないと出ないリンクがあり、再現性がない |
| エッジのラベル | 付けない | リンクの文言を取るには JSX の構造解析が要る。遷移の意味は Design Doc のシナリオに書く |
| 遷移の抽出方法 | 正規表現で `to="…"` を拾う | TypeScript の AST: 正確だが、この規模では正規表現で十分。`to` に変数を渡す書き方はしない（AGENTS.md に書く） |
