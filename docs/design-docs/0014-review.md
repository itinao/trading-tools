## 1. 背景と目的

M4 までで、事実（株価・ニュース・開示・財務）と評価（判定・スコア・シグナル・アクション・助言）と人の対応（対応した / 見送り、メモ）がすべて時点付きで残っている。ただし今の画面は「今どうか」を見るためのもので、**過去の判断を振り返って改善に使う**（0001 G5、U6）ことはできない。

本書では、既にあるデータを **時系列に並べ直す** ことで次を可能にする。

1. 銘柄ごとに「何が起きて、何を検知し、何を助言し、自分はどう判断し、その後どうなったか」を 1 本の時間軸で見る
2. 過去の判断（対応した / 見送り）を一覧し、**判断時点の株価とその後の株価** を並べて、判断と助言の妥当性を見る

新しいテーブルは作らない。すべて既存のデータから導出する。

## 2. スコープ / 非スコープ

### スコープ

- 銘柄詳細の **タイムライン**: シグナル・アクション（状態の変化）・助言・影響の大きい判定（`impact ≥ 2`）・週次のスコアを、その日の株価と一緒に時系列で表示。株価とスコアの小さな折れ線（インライン SVG）
- **履歴** 画面（`/history`）: 対応済み・見送りにしたアクションの一覧。判断日、銘柄、種類、助言の stance、自分の判断とメモ、判断時点の株価、今の株価、その後の変化率。stance × 判断の集計
- `review` ツール: エージェントが振り返りに使う `timeline <code>` と `history`（画面と同じデータを JSON で）
- スキル `retrospect`: 月に 1 回、履歴から「助言が外れた／当たった傾向」と「閾値の調整案」を報告する（提案だけ。設定は人が変える）

### 非スコープ

- 損益の集計（実現損益、資産推移）。楽天証券 CSV にあるが、取り込んでいない。別の Design Doc
- 助言の自動評価（正解率のような指標）。判断の良し悪しは株価だけでは決まらない。数値は並べるが点数は付けない
- チャートライブラリの導入。折れ線は素の SVG で最小限

## 3. 設計

### 3.1 タイムライン（銘柄詳細）

1 日を 1 行にまとめず、**出来事ごとに 1 行**。新しい順。各行にその日の株価（無ければ直近）と、今の株価との差（%）を付ける。

| 種類 | 行の内容 | 出典 |
| --- | --- | --- |
| シグナル | kind、重大度、値 | `signals` |
| アクション | 作成 / 対応した / 見送り / 未対応に戻した、メモ | `actions`（`created_at`、`resolved_at`） |
| 助言 | stance、タイトル | `actions`（`origin = ai`） |
| 判定 | 見出し・表題、sentiment / impact、要約（`impact ≥ 2` のみ） | `assessments` + `news_items` / `disclosures` |
| スコア | 週の最初の営業日のスコア（週次の点） | `scores` |
| 保有の変化 | スナップショット間で数量が変わった（買い増し・売却） | `holdings` の差分 |

- 既定は直近 90 日。「すべて」で全期間
- 折れ線: 株価（1 年）とスコア（あるだけ）。幅いっぱい・高さ 48px の SVG。目盛りは最小値・最大値だけ。アクションの日に小さな印

### 3.2 履歴（`/history`）

| 列 | 内容 |
| --- | --- |
| 判断日 | `resolved_at` |
| 銘柄 | リンク |
| 種類 | kind のラベル、守り / 攻め |
| 助言 | stance のバッジ（助言が無ければ「—」） |
| 判断 | 対応した / 見送り、メモ |
| 判断時の株価 | `resolved_at` の日の株価（無ければ直近） |
| 今の株価 | 最新 |
| その後 | 変化率（%）。守りの `reduce` を「対応した」なら下落が「助言どおり」、ウォッチの `candidate` を「対応した」なら上昇が「助言どおり」 |

- 上部に集計: stance × 判断 の件数と、その後の変化率の中央値。例: 「reduce → 対応した: 3 件、その後の中央値 -4.2%」
- 「対応した」の意味はアクションによって違う（売った、買った、確認しただけ）。**メモに何をしたか書く運用** を README に書く。集計は参考値
- フィルタ: 期間、守り / 攻め、stance、判断

### 3.3 `review` ツール

```
pnpm review timeline <code> [--days 90]     # 銘柄のタイムライン
pnpm review history [--since YYYY-MM-DD]    # 判断の履歴と集計
```

出力は画面と同じデータ。エージェントの `retrospect` スキルが読む。

### 3.4 スキル `retrospect`

1. `pnpm review history --since <30 日前>` を読む
2. stance × 判断 × その後の変化率を見て、傾向を **事実として** 列挙する（「reduce と助言した 3 件のうち 2 件はその後 +5% 以上」など）
3. `config/detect.json` の閾値について、根拠つきの調整案を出す（例: 「`drawdown_60d` の warn -15% は 8 件中 6 件がその後戻しており、-20% に緩める案」）。**設定は変えない**。人が判断して変える
4. 助言の書き方の改善点があれば、`advise` スキルへの追記案を出す

## 4. 検討した選択肢と決定

| 論点 | 決定 | 却下した選択肢と理由 |
| --- | --- | --- |
| データの持ち方 | 導出（テーブル追加なし） | 「出来事」テーブルを別に持つ: 既存データと二重になり、ずれる |
| 判断の評価 | 数値を並べるだけ。点数は付けない | 正解率: 「対応した」の意味が一定でなく、株価だけで良し悪しは決まらない |
| 折れ線 | 素の SVG | チャートライブラリ: 依存が増え、DESIGN.md の「装飾なし」に反しやすい。必要な情報は最小値・最大値と印だけ |
| 振り返りの主体 | 人（画面）+ エージェント（`retrospect` は提案のみ） | エージェントが閾値を自動調整: 根拠の検証を人が飛ばすことになる |

## 5. リスク・未決事項

| # | 内容 | 対応 |
| --- | --- | --- |
| R1 | 「対応した」の内容が分からず、集計が意味を持たない | メモの運用を README に書く。M6 以降で「対応した」に種別（売った / 買った / 確認した）を持たせることを検討 |
| R2 | データがまだ少なく、傾向が出ない | 1〜3 か月の運用後に `retrospect` を回す前提。画面は初日から使える |

## 要確認

1. 履歴の集計は「件数と中央値」だけ（正解率のような点数は付けない）でよいか
2. `retrospect` は提案だけで、設定の変更は人が行う、でよいか
3. 損益の集計（実現損益・資産推移）は別の Design Doc に分けてよいか
